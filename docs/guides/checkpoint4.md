# ASTROWORLD: Checkpoint 4, ray tracing and completion

## Summary

Checkpoint 4 completed ASTROWORLD by adding a third renderer, a CPU ray tracer that draws the same `ParkScene` as the OpenGL program, with the same shapes, materials, camera, sky, textures and animation time. Whitted ray tracing gives true shadows and reflections, shown off by a chrome mirror ball, and a path tracer adds global illumination, with soft, light-filled shadows and colour bleeding, using next-event estimation, Russian roulette and tone mapping. A bounding volume hierarchy, Möller–Trumbore triangle tests and multi-threading make it practical, supersampling provides anti-aliasing, and it can render through any of the prototype's projections. Its timings, about 11 seconds for a clean image and nearly 3 minutes for a path-traced one, against about 80 frames per second for OpenGL, show why games rasterize and films ray trace. The stage also includes the Checkpoint 4 report, which sets out what works, what doesn't and what should come next.

## In detail

Checkpoint 4 is the course's fourth and last checkpoint. The brief was to refine and complete the project, present a final demonstration, say honestly what works and what doesn't, and recommend what should come next. By this point the project already had two ways of drawing the park: the 2D software renderer from Checkpoints 1 and 2, where every pixel came from our own line, curve and fill algorithms, and the real-time 3D park on the graphics card from Checkpoint 3 and the prototype. Checkpoint 4 adds a third renderer, a ray tracer, which draws the very same 3D park the way light really behaves. It covers the last topics in the syllabus: ray tracing, global illumination and anti-aliasing.

The main difference between the ray tracer and the OpenGL version is the direction in which they work. OpenGL works object by object: it takes each triangle and asks which pixels it covers. A ray tracer works pixel by pixel. For every pixel it sends a ray from the eye into the scene and asks what that ray hits first. From that point it sends more rays: one towards the sun to check whether the point is in shadow, and, for shiny surfaces, one in the mirror direction to see what is reflected. This is called Whitted ray tracing, and it gives naturally sharp shadows and true reflections, which the real-time version couldn't do. To show off reflections we added a chrome mirror-ball sculpture to the park. Because it is curved, it reflects the whole park in a bent, fish-eye way.

Importantly, the ray tracer doesn't have its own copy of the park. It reads exactly the same scene description the OpenGL program draws, the `ParkScene` we introduced in the prototype, with the same shapes, materials, camera, lighting and animation time. Even the sky was translated from the graphics-card shader into C++, and the textures are drawn once and shared, so both renderers show the identical park at any moment.

On top of that, Checkpoint 4 includes a path tracer, which produces global illumination. Whitted ray tracing follows only perfect mirror bounces. A path tracer also lets light bounce off dull, matte surfaces in random directions, which is how light behaves in the real world. As a result, light bounces off the ground into shadowed areas, colours bleed softly onto nearby surfaces, and the sky lights the whole scene gently, so shadows become soft and filled with light instead of black. Because the bounces are random, each pixel is an average of many light paths, and the image is grainy until enough paths are added. Two techniques keep this efficient. With next-event estimation, every bounce aims a ray straight at the sun instead of hoping a random bounce finds it. With Russian roulette, weak light paths are randomly stopped early, and the surviving ones are boosted so the overall result stays accurate. The bulbs and the glowing mouth of the head act as real light sources, which makes the night scenes especially atmospheric. The path tracer produces brightness beyond what a screen can show, so tone mapping gently compresses the bright areas instead of flattening them to pure white.

Making this practical required careful engineering. The park contains about 92,000 triangles, and testing every ray against every one would be hopelessly slow. So before rendering we build a bounding volume hierarchy, a tree of boxes inside boxes around groups of triangles. A ray that misses a box can skip everything inside it, so it only has to test a handful of triangles. The tree takes about a quarter of a second to build. Each ray is tested against triangles with the Möller–Trumbore algorithm, a standard and efficient method, and the work is spread across all of the computer's processor cores. Anti-aliasing is done by supersampling: each pixel is sampled several times at slightly jittered positions within it, and the results are averaged, which smooths jagged edges and fine detail. The ray tracer can also render through any of the projections from the prototype, such as isometric or oblique, by working backwards from each pixel through the camera's projection.

The performance numbers tell a clear story about computer graphics. Our 2D software renderer draws about 15 to 20 frames per second. OpenGL on the graphics card manages about 80, but the same OpenGL program forced onto the processor drops to about 14. The ray tracer takes about 11 seconds for a clean Whitted image, and the path tracer nearly 3 minutes for a high-quality one. That is why games rasterize and films ray trace.

Completing the project also meant writing the Checkpoint 4 report. Every topic in the course is implemented, visible, and mapped to the code that does it, from raster graphics and colour models through the line, circle, curve and fill algorithms, clipping, transformations, every projection, the three shading modes, texture mapping and mipmaps, to ray tracing, path tracing and anti-aliasing. All three renderers share the same colours, curves, mathematics and animation timeline, and the park runs as a 30-second animated loop from day through dusk and night to dawn, with every ride moving. The report is also honest about the shortcomings. The 3D head's nose, lips and eyelids are simple rounded shapes, so it looks blobby up close, and its mouth is a glowing panel rather than a real opening. The real-time version has no shadows; only the ray tracer has them. The ray tracer is too slow to be interactive and has no noise reduction, and the searchlight beams exist only in the OpenGL version. The report recommends real-time shadow mapping, physically based materials and high-dynamic-range lighting in the real-time renderer, a faster ray tracer, and a properly sculpted head with a walk-through mouth. Most of these were carried out afterwards, when we took the project a step further with the photorealism and Blender stages.

In short, Checkpoint 4 completes ASTROWORLD with a third, physically accurate way of seeing the same park. The ray tracer gives true shadows and reflections, the path tracer gives soft, realistic global illumination, and an acceleration structure and multi-threading make it practical. Together with an honest account of what was achieved, what fell short and where the project should go next, it rounds off a journey from drawing single pixels by hand to simulating how real light moves through a scene.
