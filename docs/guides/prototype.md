# ASTROWORLD: Prototype, integration

The Prototype stage is where we brought all the different parts of the project together into one working, interactive 3D program.

Before this stage, the project existed as three separate checkpoints. In Checkpoint 1, we built a 2D renderer using our own C++ code to draw everything, from lines and circles to curves and filled shapes. Checkpoint 2 introduced transformations and animation, bringing the park to life through a 30-second day-to-night cycle. Then, in Checkpoint 3, we rebuilt the park in 3D using OpenGL, with our own models and shaders. The main goal of the Prototype was to combine all these components into one functional program, while also demonstrating the remaining graphics concepts from the course.

One of the biggest changes we made during this stage wasn't necessarily something you could see on screen. We separated the description of the park from the actual process of rendering it. We introduced something called `ParkScene`, which essentially describes what the park looks like at any given moment. It contains a list of objects, with each object having a shape, a transformation matrix that determines its position and orientation, and a material that defines its colour and shininess. The scene also contains information about lighting.

The important thing here is that this description doesn't depend on OpenGL or any particular graphics library. The OpenGL renderer simply reads the scene and draws whatever it finds there. This also means we can reuse the same shape multiple times in different positions. More importantly, because the park is described independently of the renderer, our ray tracer can render that exact same park without needing a separate scene description. We also moved the 3D models of the head, rides and camera into a shared folder so that all our rendering systems could use the same assets.

On top of that foundation, we implemented different types of shading interpolation. This is essentially about where lighting calculations happen across the surface of a model. With flat shading, lighting is calculated once for each triangle, so you can clearly see the individual faces that make up a surface. Gouraud shading calculates lighting at the corners of each triangle and blends the results across the surface, which makes things look smoother, although some highlights can become less visible. Phong shading goes a step further by interpolating the surface normals and calculating lighting at every pixel. This produces much sharper and more accurate-looking highlights. All three methods use the same lighting model; the main difference is where the calculations take place. We also included a wireframe view so we can see the triangles that make up each model.

We also implemented the different projection types covered in the course, which determine how we represent a 3D world on a 2D screen. These include the normal perspective projection, where objects further away appear smaller, and isometric projection, where the camera looks at the scene diagonally while keeping parallel lines parallel. We also have cavalier and cabinet projections, which are types of oblique projection. Both represent depth using diagonal lines, but cavalier keeps the full depth length while cabinet reduces it by half, making the result look a little more natural.

We included top and front views as well, which give us the equivalent of engineering plans and elevations. Finally, we implemented one-point, two-point and three-point perspective. These determine how many sets of parallel lines converge towards vanishing points, depending on the camera's position and orientation.

Another area we covered was texture mapping and mipmapping. For the ground, we used a concrete texture with visible slabs, joints and spilled popcorn to make the plaza resemble the original album cover. What's particularly interesting is that this texture was created using our own 2D renderer from Checkpoint 1. We then tiled it across the ground in the 3D scene, which brings the very first stage of the project into the prototype. The lettering on the park sign is also applied as a texture.

Mipmapping helps improve how these textures look at different distances. Instead of using one texture at every distance, we store smaller versions of it and allow the graphics card to select the appropriate version depending on how far away the surface is. Without mipmapping, distant textures tend to shimmer and flicker as the camera moves. With it, the ground looks much more stable.

We also wanted the park to feel a little more alive, so we added a few features to improve the atmosphere and interactivity. At night, searchlight beams sweep across the sky. These are represented using cones with additive blending, meaning their light is added to the existing scene without completely hiding whatever is behind them.

We also implemented a first-person roller coaster experience. You can ride from the front car of the train and look ahead as it moves along the track. The interesting part is that the train's speed still uses the energy-conservation physics we developed in Checkpoint 2, so it naturally accelerates as it moves down drops in the track. We also made it possible to run the different views and rendering modes from the command line, which is how we generated the evidence images for this stage.

Ultimately, the Prototype brought together what had previously been a collection of separate experiments and turned them into one complete, working program. We now have a park that is described once and can be rendered by different systems, with different shading methods and projection types that can be switched and demonstrated live. We also have mipmapped textures, searchlights, an interactive roller coaster and several other features that make the environment feel more complete. Most importantly, the structure we established here gave us the foundation for the ray-traced version of ASTROWORLD in Checkpoint 4.
